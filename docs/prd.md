## 1. 개요

### 1.1 배경
CAD 도면과 기술 문서를 고객사에 전달한 뒤에는 회사가 해당 파일의 사용을 통제할 수 없습니다. 프로젝트 종료 후에도 도면이 고객사 내부에 남거나, 제3자(경쟁 협력사 등)에게 재전달되어도 이를 인지하거나 회수할 방법이 없습니다.

### 1.2 문제 정의
| 문제 | 현재 상태 | 영향 |
|---|---|---|
| 기간 통제 부재 | 전달된 파일은 영구 열람 가능 | 계약 종료 후에도 기술 자산 노출 |
| 수신자 통제 부재 | 파일만 있으면 누구나 열람 | 무단 재배포 시 유출 범위 확산 |
| 회수 불가 | 오발송·계약 해지 시 대응 수단 없음 | 사고 발생 후 피해 확산 차단 불가 |
| 추적 불가 | 누가 언제 열람했는지 알 수 없음 | 유출 시 경로 특정 및 책임 소재 불명확 |

### 1.3 제품 비전
> 고객사에 전달한 도면과 문서를, **정해진 사람만, 정해진 기간 동안, 보기만** 할 수 있게 하고, 필요할 때 **언제든 회수**할 수 있게 한다.

## 2. 목표와 비목표

### 2.1 목표 (Goals)
| ID | 목표 |
|---|---|
| G1 | 등록된 수신자만 문서를 열람할 수 있다. |
| G2 | 지정된 열람 기간이 지나면 이미 전달된 파일도 열람할 수 없다. |
| G3 | 발신자가 언제든 특정 문서·수신자의 열람 권한을 회수할 수 있다. |
| G4 | 열람은 가능하되 저장·인쇄·복사·화면 캡처를 차단한다. |
| G5 | 모든 열람 시도(성공·거부)를 기록하고, 화면 워터마크로 유출 경로를 추적할 수 있다. |
| G6 | 2D/3D CAD, PDF, Office 문서를 단일 체계로 보호한다. |

### 2.2 비목표 (Non-Goals)
| 항목 | 사유 |
|---|---|
| 원본 CAD 프로그램(AutoCAD 등)에서의 열람·편집 | 에이전트형 DRM 영역. 개발·운영 비용 대비 효과 낮음 |
| 사내 문서 보안(내부 유출 방지) | 외부 배포 통제에 집중. 사내 DRM은 별도 제품 영역 |
| 사진 촬영 등 아날로그 유출 차단 | 기술적으로 불가. 워터마크 기반 추적으로 대체 |
| macOS·Linux·모바일 전용 뷰어 | 1차 범위 제외. 웹 뷰어로 대체 |
| 고객사가 수정한 문서의 재수신(양방향 협업) | 열람 전용 제품 |

## 3. 사용자

| 페르소나 | 설명 | 핵심 니즈 |
|---|---|---|
| **발신자** (사내 영업·설계 담당) | 고객사에 도면·문서를 전달하는 실무자 | 빠르고 간단한 등록, 열람 현황 확인, 즉시 회수 |
| **수신자** (고객사 담당자) | 전달받은 문서를 열람하는 외부 사용자 | 복잡한 절차 없이 열람, 설치 부담 최소화 |
| **보안 관리자** (사내 정보보안 담당) | 전사 정책 및 감사 책임자 | 전사 기본 정책 설정, 감사 로그 조회, 사고 대응 |
| **시스템 관리자** | 서버·인프라 운영 담당 | 안정적 운영, 키 관리, 장애 대응 |

## 4. 사용자 시나리오

### S1. 문서 배포 (발신자)
1. 발신자가 포털에 로그인하여 파일(DWG, STEP, PDF, DOCX 등)을 업로드한다.
2. 수신자 이메일 목록, 열람 기간(시작일~만료일), 권한 옵션(온라인 전용 여부, 웹 열람 허용 여부)을 지정한다.
3. 시스템이 파일을 중간 포맷으로 변환·암호화하고 `.drm` 파일과 웹 열람 링크를 생성한다.
4. 수신자에게 안내 메일이 발송된다.

### S2. 문서 열람 — 전용 뷰어 (수신자)
1. 수신자가 `.drm` 파일을 더블클릭하면 전용 뷰어가 실행된다. (미설치 시 안내 메일의 링크로 설치)
2. 최초 1회 이메일 OTP 인증 및 기기 등록을 수행한다.
3. 서버가 수신자·기간·회수 여부를 검사하고 라이선스를 발급한다.
4. 문서가 수신자 워터마크와 함께 표시된다. 저장·인쇄·복사·캡처는 차단된다.

### S3. 문서 열람 — 웹 (수신자)
1. 안내 메일의 링크를 클릭하여 이메일 OTP로 인증한다.
2. 브라우저에서 워터마크가 적용된 문서를 열람한다.

### S4. 권한 회수 (발신자)
1. 발신자가 포털에서 문서 또는 특정 수신자를 선택하여 회수한다.
2. 이후 해당 수신자의 모든 열람 요청이 거부된다. 열람 중인 세션은 라이선스 만료 시점에 종료된다.

### S5. 만료
1. 열람 기간이 지나면 서버가 라이선스 발급을 거부한다.
2. 수신자에게는 "열람 기간이 만료되었습니다. 발신자에게 문의하세요." 메시지와 발신자 연락처가 표시된다.

### S6. 기간 연장·수신자 추가 (발신자)
1. 발신자가 기존 배포 건의 만료일을 연장하거나 수신자를 추가한다.
2. 파일을 재전달할 필요 없이 기존 `.drm` 파일에 즉시 반영된다.

### S7. 유출 조사 (보안 관리자)
1. 외부에서 발견된 캡처 이미지의 워터마크로 수신자와 열람 시각을 식별한다.
2. 감사 로그에서 해당 수신자의 열람 이력(기기, IP, 시각)을 조회한다.
3. 해당 수신자의 전체 권한을 일괄 회수한다.

## 6. 비기능 요구사항

### 6.1 보안
| ID | 요구사항 |
|---|---|
| NFR-S1 | 파일 본문은 AES-256-GCM으로 암호화하고, 파일별 CEK는 KMS 마스터키로 봉투 암호화한다. |
| NFR-S2 | 기간·수신자·회수 정책은 서버에서만 판정한다. 클라이언트 시계·설정에 의존하지 않는다. |
| NFR-S3 | 클라이언트에는 장기 비밀을 보관하지 않는다. 복호화 키는 단기 라이선스(기본 수명 10분)로만 전달한다. |
| NFR-S4 | 복호화된 평문은 메모리에서만 처리하며 디스크(임시 파일 포함)에 기록하지 않는다. |
| NFR-S5 | `.drm` 헤더는 서버 서명으로 위변조를 탐지한다. |
| NFR-S6 | 모든 통신은 TLS 1.2 이상을 사용한다. |
| NFR-S7 | 로그에 키·OTP·문서 내용 등 민감정보를 기록하지 않는다. |
| NFR-S8 | 원본 업로드 파일은 패키징 완료 후 정책에 따라 삭제 또는 암호화 보관한다. |
| NFR-S9 | 정식 출시 전 외부 모의해킹(뷰어 리버싱 포함)을 수행한다. |

### 6.2 성능 (목표치 초안)
| ID | 요구사항 |
|---|---|
| NFR-P1 | 라이선스 발급 응답: p95 300ms 이하 |
| NFR-P2 | 50MB PDF 첫 페이지 표시: 3초 이하 (라이선스 발급 포함) |
| NFR-P3 | 패키징(변환 제외): 100MB당 10초 이하 |
| NFR-P4 | 변환 작업은 비동기 큐로 처리하며 API 응답을 지연시키지 않는다. |

### 6.3 가용성·확장성
| ID | 요구사항 |
|---|---|
| NFR-A1 | 라이선스 서버 가용성 99.9% (라이선스 서버 장애 = 전 고객사 열람 불가이므로 최우선) |
| NFR-A2 | API 서버·변환 워커는 수평 확장 가능한 무상태(stateless) 구조 |
| NFR-A3 | 동시 열람 세션 1,000건 이상 처리 (초기 목표) |

### 6.4 호환성
| ID | 요구사항 |
|---|---|
| NFR-C1 | 전용 뷰어: Windows 10 (22H2) 이상, x64 |
| NFR-C2 | 웹 뷰어: 최신 Chrome, Edge (WebGL 2.0 필수) |
| NFR-C3 | 고객사 프록시 환경에서 HTTPS(443)만으로 동작 |
| NFR-C4 | `.drm` 포맷은 버전 필드로 하위 호환성을 보장한다. |

### 6.5 운영·감사
| ID | 요구사항 |
|---|---|
| NFR-O1 | 감사 로그는 변경 불가(append-only)로 저장하고 최소 3년 보관 |
| NFR-O2 | 구조화 로그(JSON)와 요청 추적 ID(correlation ID) 적용 |
| NFR-O3 | KMS 마스터키 교체(rotation) 시 기존 문서 재암호화 없이 운영 가능 |

## 7. 정책 모델

## 14. 단계별 개발 계획 (바이브 코딩)

AI 코딩 도구(Claude Code 등)로 개발하는 것을 전제로, **AI가 한 세션에 끝낼 수 있고 사람이 검증할 수 있는 크기**로 작업을 나눴습니다.

### 14.1 진행 원칙

| 원칙 | 내용 | 이유 |
|---|---|---|
| 1 작업 = 1 세션 = 1 커밋 | 작업 하나를 끝내고 검증·커밋한 뒤 다음 작업으로 넘어갑니다. | 범위가 커지면 AI가 맥락을 잃고, 문제가 생겼을 때 되돌리기 어렵습니다. |
| 스펙·인터페이스 먼저 | 공용 계약(`packages/contracts`)과 포맷 스펙을 먼저 고정하고 구현은 그 뒤에 합니다. | AI가 앱마다 다른 타입을 임의로 만들어내는 것을 막습니다. |
| 테스트로 완료 판정 | 모든 작업은 "완료 기준"의 명령(테스트·빌드)이 통과해야 끝납니다. | "잘 동작합니다"라는 AI의 자체 보고를 그대로 믿지 않기 위함입니다. |
| 암호 기능 직접 구현 금지 | Node 내장 `crypto`(AES-256-GCM, X25519, Ed25519, AES-KW)와 검증된 라이브러리만 조합합니다. | AI가 암호 알고리즘을 직접 짜거나 잘못 조합하는 것이 가장 위험한 실패입니다. |
| 보안 핵심 코드는 사람 리뷰 필수 | 🔒 표시 작업은 사람이 코드를 직접 읽고 승인한 뒤 커밋합니다. | 테스트가 통과해도 설계 결함(논스 재사용, 정책 우회 등)은 남을 수 있습니다. |
| 프로젝트 CLAUDE.md 유지 | 기술 스택, 명령어, 폴더 규칙, 금지 사항을 프로젝트 루트 `CLAUDE.md`에 기록하고 작업마다 갱신합니다. | 세션이 바뀌어도 AI가 같은 규칙으로 작업합니다. |

[작업 ID] T1-03 컨테이너 포맷 구현
